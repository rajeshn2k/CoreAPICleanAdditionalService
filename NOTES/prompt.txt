Objective
Migrate the application's custom Polly-based resilience implementation for RabbitMQ and Redis to the modern Microsoft.Extensions.Resilience + Polly ResiliencePipeline model.

The resilience implementation must support:

Retry

Circuit Breaker

Timeout

for:

RabbitMQ operations

Redis operations

Also remove Microsoft.Extensions.Http.Polly because it is not required for this migration.

Do NOT use Microsoft.Extensions.Http.Resilience for RabbitMQ or Redis. Microsoft.Extensions.Http.Resilience is intended for HttpClient resilience. For RabbitMQ and Redis, use Microsoft.Extensions.Resilience and Polly ResiliencePipeline.

Retry configuration
Configure retry using the modern:

RetryStrategyOptions

Use exponential backoff and jitter.

Example baseline:

new RetryStrategyOptions
{
    MaxRetryAttempts = 3,
    Delay = TimeSpan.FromSeconds(1),
    BackoffType = DelayBackoffType.Exponential,
    UseJitter = true
}

Adjust the values only if existing application configuration clearly specifies different retry behavior.

Do not retry cancellation exceptions.

Do not retry errors that should not be retried if the existing code or client library allows those errors to be distinguished.

For RabbitMQ and Redis, prefer transient-failure handling rather than blindly retrying every possible exception.

If exception predicates need to be customized, document why.

Circuit breaker configuration
Use:

CircuitBreakerStrategyOptions

Do NOT translate the old:

exceptionsAllowedBeforeBreaking

Treat these as baseline values, not unquestionable requirements.

If the existing application has explicit production settings for failure thresholds, preserve their intent and map them appropriately to the new failure-ratio model.

Add structured logging/telemetry for:

public sealed class ResilientMessagePublisher : IMessagePublisher

RabbitMQ failure behavior
Pay particular attention to this existing behavior:

catch (BrokenCircuitException)
{
    logger.LogWarning(...);
}

Do NOT silently return success after a message was not published unless the application's existing messaging semantics explicitly require best-effort fire-and-forget behavior.

Prefer:

catch (BrokenCircuitException ex)
{
    logger.LogWarning(ex, ...);
    throw;
}

This allows the caller to know that publishing failed.

Do not blindly catch:

catch (Exception)

and convert a failed message publish into apparent success.

If the existing application intentionally treats publishing as best-effort, preserve that behavior only after verifying it from the surrounding code and document the decision.
